# Промпты

Боевой промпт — [`prompts/extract_card.md`](../prompts/extract_card.md). Его история видна в git. Здесь описано, почему он устроен именно так и как менялся по результатам eval.

## Как собирается запрос

- **system** — промпт из `prompts/extract_card.md`; вместо `{catalog}` подставляется справочник из `data/products.json` (id, название, синонимы).
- **user** — текст письма как есть, вместе с заголовками «От / Дата / Тема». Дата нужна, чтобы посчитать относительные сроки.
- Если ответ не прошёл валидацию, модель получает один повторный запрос: её ответ + текст ошибки Pydantic + «верни исправленный JSON целиком».

## v1

Решения и почему так:

| Решение | Зачем |
|---|---|
| «Нет данных → null, ничего не додумывай» отдельным первым правилом | Пустое поле менеджер заполнит сам, а выдуманный телефон уйдёт в CRM и потеряет клиента |
| Явно сказано, что клиент — отправитель, а не контакты из пересланных писем и не «СеверТех» | Самая частая ошибка ручного переноса — взять не тот контакт из цепочки (письмо 02) |
| Справочник продуктов целиком в промпте, с синонимами | 13 позиций целиком помещаются в контекст, RAG не нужен. Синонимы помогают, когда клиент пишет своими словами (письмо 03) |
| Правило срочности с порогом «3 рабочих дня» и дедлайн от даты письма | Без явного правила модель и менеджеры понимают «срочно» каждый по-своему |
| `evidence` — дословная цитата для каждого поля | Даёт код-проверку на галлюцинации без второй модели: цитату ищем в письме (`find_unconfirmed`) |
| Образец JSON в конце промпта, «только JSON без markdown» | `response_format` с JSON-схемой у GigaChat не гарантирован; формат держим промптом + Pydantic + повтор |

### Результаты v1

GigaChat-2-Max, 4 письма. Полный отчёт — [`eval/v1.md`](eval/v1.md), ответы модели — [`eval/v1.json`](eval/v1.json).

| Метрика | v1 |
|---|---|
| Компания, email, телефон, срочность, продукты | 4/4 по каждому полю |
| Дедлайн | 3/4 |
| Писем без ошибок в строгих полях | 3/4 |
| Полей без подтверждающей цитаты | 9 |
| Токены на письмо | ~1100 |
| Время | 8.2 с в среднем, 9.8 с максимум |

Главное: ловушку с пересланной перепиской (02) модель прошла, контакты и компании извлекаются верно. Ошибки такие:

1. **Дедлайн «до пятницы» посчитан неверно (04).** Письмо от четверга 22.10, модель выдала 27.10 (вторник). LLM плохо считает даты и дни недели — это нужно делать не промптом, а подсказкой из кода.
2. **Нет цитат для продуктов (все 4 письма) и для дедлайна (01).** Модель пропускает ключи `products[i]` или пишет их по-своему (`products[0].name_in_email`). В образце JSON в промпте были только два ключа evidence — модель повторяет образец.
3. **Суть запроса теряет детали.** Нет количества дизайнеров и вопроса о ценах (03), нет того, что это претензия и что склад стоит (04), нет причины смены поставщика (02). Для менеджера это главное поле, по нему он решает, что делать.
4. **Мелочи:** у услуги монтажа придуман `quantity: 1` (01), для сути запроса в 03 приведена нерелевантная цитата, в 03 нет `reason` у срочности.

Ограничение самой проверки: она подтверждает, что цитата есть в письме, но не что цитата обосновывает значение поля (как в п. 4). Для email и телефона это можно усилить сверкой самого значения с текстом.

## v2

Что поменяли по итогам v1:

| Проблема v1 | Что сделали | Где |
|---|---|---|
| Дедлайн «до пятницы» посчитан неверно | Код достаёт дату письма из заголовка и передаёт модели день недели и ближайшую дату для каждого дня недели. Модель не считает, а выбирает готовую | `date_hint()` в `app/extractor.py` + правило 7 |
| Нет цитат для продуктов и дедлайна | Полный образец `evidence` со всеми ключами, включая `products[0]`, `products[1]`; явное «заполни ключ для каждого непустого поля» | правило 8 + образец JSON |
| Суть запроса теряет детали | Структура: тип обращения → что и сколько → контекст | правило 5 |
| Придуманное количество у услуг | «Для услуг и когда число не названо — null», пример косвенного количества | правило 6 |

Первый вариант подсказки с датой не сработал, и это показательно. Сначала давали календарь на 14 дней вперёд с днями недели — модель 3 раза из 3 выбрала пятницу через неделю (30.10 вместо 23.10). Заменили на список «ближайший понедельник, …, ближайшая пятница» — 3 из 3 верно. Вывод: модели нельзя оставлять даже выбор из списка, если ответ можно подготовить кодом.

### Результаты v2

Полный отчёт — [`eval/v2.md`](eval/v2.md), ответы модели — [`eval/v2.json`](eval/v2.json).

| Метрика | v1 | v2 |
|---|---|---|
| Писем без ошибок в строгих полях | 3/4 | **4/4** |
| Дедлайн | 3/4 | **4/4** |
| Полей без подтверждающей цитаты | 9 | **1** |
| Токены на письмо | ~1100 | ~1250 |
| Время, среднее / максимум | 8.2 / 9.8 с | 10.3 / 12.5 с |

Что осталось:

- **Единственная неподтверждённая цитата — ложная тревога.** Модель привела «монтаж и пусконаладка» в начальной форме, а в письме «монтажом и пусконаладкой». Значение верное; менеджер увидит ⚠️ на правильном поле. Это допустимо: лишняя проверка дешевле пропущенной ошибки.
- **Суть запроса стала лучше, но контекст всё ещё теряется.** Тип обращения и количество есть («Претензия: …», «для 6 дизайнеров»), но нет «текущий поставщик не устроил сроками» (02) и интереса к договору техподдержки (04). Продукт техподдержки при этом попал в `products`, так что для CRM информация не потеряна.
- **Время выросло до ~10 с** из-за более длинного ответа (цитаты на все поля). Для обработки входящей почты в фоне это нормально; для интерактивного сценария стоит сравнить с GigaChat-2-Pro.
